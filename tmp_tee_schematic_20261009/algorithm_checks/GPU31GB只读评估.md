# D=8、χ=64–80、float64：31 GB GPU只读评估

> **旧实现的只读资源审计，以下内容保留当时状态。** 下文“每个扇区仍保存完整 χ⁴ 向量、没有三角压缩”等描述已过时：当前代码已实现实际 packed replica 扇区，并修复求谱器；采用最大 64 维 basis、block4。修复依据见 [Krylov修复与回归](../local_gpu_validation_20261009/Krylov修复与回归.md)。真实 0713summary tensor 的 **D2–6 本机 GPU 测试现已全部通过，严格 gate=True**；实测资源和状态见[本机GPU验证结果](../local_gpu_validation_20261009/本机GPU验证结果.md)。D8 尚未在本机做同等规模验证；下文的旧数组预算与优化建议用于对照，不代表 D8 当前实测显存。

本文件只根据当前两个生产候选脚本的数组形状与运算计数评估；没有修改求谱实现，没有运行高D计算，也没有给出未经测量的小时数。只有物理routine已被单独正面核对后，才应把本文件作为下一步工程优化建议。

## 当前实现与背景方案的区别

当前 `renyi2_twoc3.py` / `renyi2_spectral.py`：

- 全程使用实数float64，T₂向量长χ⁴。
- 同时缓存Q与T₂Q，分别预分配 `χ⁴ × subspace`。
- 两个replica交换扇区依次求解；每个扇区仍保存完整χ⁴向量。`project()`仅投影，并没有三角压缩存储。
- matvec使用完整八步精确收缩，第一条输出χ腿分批。没有实现背景的单扇区剪枝，也没有同时推进两个扇区。
- 每一组 `--modes` 从头开始求谱，没有延续上一组已算出的子空间。
- `einsum`目前依赖框架排列大工作数组，没有显式实现背景描述的gather–GEMM–scatter与固定缓冲复用。

因此，背景“25–26 GiB”的complex128预算不能直接照搬。虽然实数存储减半，当前缓存Q和T₂Q又使basis存储翻倍；两项在χ=64、80维basis时恰好抵消。

## 可核实的主要数组大小

31十进制GB = 28.871 GiB。以下GiB均为2³⁰字节，尚未计CUDA上下文、库workspace及allocator余量。

| 数组 | χ=64 | χ=80 |
|---|---:|---:|
| 一条完整float64向量 | 0.125 | 0.30518 |
| 完整Q+T₂Q，subspace=80 | 20.000 | 48.828 |
| 完整Q+T₂Q，subspace=64 | 16.000 | 39.063 |
| 对称扇区一条压缩向量 | 0.06252 | 0.15261 |
| 压缩Q+T₂Q，subspace=80 | 10.002 | 24.418 |
| 压缩Q+T₂Q，subspace=64 | 8.002 | 19.534 |
| 单个收缩work，batch=8 | 1.000 | 1.953 |
| 单个收缩work，batch=4 | 0.500 | 0.977 |
| 显式T₁ | 0.125 | 0.30518 |

公式：一条完整向量为8χ⁴字节，单个work为8D²·batch·χ³字节。对称/反对称扇区维数分别为χ²(χ²±1)/2。

当前收缩的相邻两级work会同时存在；框架为了reshape/GEMM也可能额外复制一个大work。因此只把单个work计入峰值不正确。当前正交化还会同时涉及原候选块、QR输出与筛选后的列；这是basis之外的显著临时分配。

**结论：当前默认subspace=80在χ=80仅Q+T₂Q就超过31 GB，确定放不下。χ=64的20 GiB常驻basis能放，但默认32模会把block自动增到16，临时分配使总峰值接近上限，不能仅凭20 GiB宣布安全。** 当前 `memory_budget()` 的保守分配项在χ=64、subspace=80、block=16、batch=8时已约31.1 GiB，也不是实测峰值证书。

## 首选安全优化

1. **真正压缩replica扇区的Q与T₂Q。** 将四指标看成χ²×χ²矩阵，只存上三角；非对角坐标乘√2保持普通欧氏内积。算matvec时仅展开当前向量，输出后压回。这是保持交换对称性后的坐标变换，不截断物理张量、不丢本征值。两个扇区都必须保留并分别求谱。

2. **控制实际block宽度。** 当前 `max(block_size,count//2)` 导致32模必用至少16列block；大block的QR临时内存不能忽略。可以从4列或8列开始，发现需要更大简并簇时再扩展，不能为了内存盲目拆掉尚未解析的简并重数。χ=80可把“压缩subspace=64、block=4–8、batch=4”作为待实测的起始配置。其Q+T₂Q为19.534 GiB，合理缓冲复用后仍有几GiB余量；必须再用实际GPU峰值确认，不能把这一估计当成现成可运行命令。

3. **缓存ABCD的GEMM布局，复用work与输出缓冲，分块完成必要的排列。** 这不改变八步收缩，但可减少每次matvec的大数组拷贝与分配。batch只改变工作集与GEMM形状，不减少主乘加量；χ=80先用4而非8更容易留出显存余量。

4. **从8模增到16/32模时延续已算子空间。** 目前每一档从同一seed重新求解，存在重复收缩。延续/扩展子空间不改变目标矩阵，通常比三次独立求解节约工作；仍应保留独立初始块的核查。

5. **按S₂的误差分配求谱精度。** 对L≤1000，p=L/2≤500。正实主根主导时，误差传播为δS₂≈2p·δλ₁/λ₁−p·δλ₂/λ₂。若两个主根相对误差各≤10⁻⁸，这部分最坏约1.5×10⁻⁵，可给谱尾留出余量。没有必要强求对迹已完全无贡献的小根达到相对自身10⁻¹⁰。对非正规矩阵，Ritz残差本身不等于本征值误差，仍需主根/最终熵的实际稳定性检查，保留相位、符号和简并重数。

上述优化都应在修复并验证正交化之后进行。压缩存储不能修复当前坏基；单纯放宽残差也不能修复坏基。

## 进一步加速的条件式候选

背景提出的“两个扇区相加，一次matvec同时推进”在算子保持replica交换的条件下有线性代数依据，但需要两个独立子空间的正交化、投影矩阵与重启；当前程序没有实现。不能直接把两个扇区交给同一个普通Krylov递推。

背景的单扇区虚指标半域剪枝如果严格保持其权重与交换补回，可减少乘加量；其小D逐项等价验证应先做，随后才测GPU速度。更多小GEMM与排列可能吃掉一部分理论收益，因此不承诺38.9%的墙钟加速。

## 运算量及时间判断

完整八步收缩的主乘加量为4D²(D+1)χ⁵；D=8时是2304χ⁵个**实数**乘加，约4608χ⁵个实浮点操作：

| χ | 完整matvec主运算量 |
|---|---:|
| 64 | 4.948 TFLOP |
| 80 | 15.099 TFLOP |

背景19.79 / 60.40 TFLOP的表格按complex128估算，不能用于当前实float64程序。相同迭代数下χ=80主运算量约是χ=64的3.052倍。只有31 GB显存容量不足以判断FP64吞吐；还需要GPU型号、实际GEMM效率和谱导致的迭代次数。因此本评估不沿用背景2–7小时的估计。

三个env pair分三个job适合当前独立算子；每个job按一个pair计算显存，三个pair的basis不需要在同一卡上同时常驻。

本文件的内存与运算量来自代码形状的直接计算；未依赖外部产品规格。
